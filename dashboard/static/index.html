One repo. Many AI agents. No shared memory.

The Acme platform team runs a Pulumi GitHub repo for infrastructure-as-code across AWS, Cloudflare, and Okta. Increasingly that code is written by AI coding agents - and each one works blind and alone.

The codebase

A Pulumi (TypeScript) monorepo. Reusable component libraries (S3Bucket, PostgresDatabase, DnsRecord, SsoApplication) composed into production and staging environments.

The agents

Three different AI coding tools, used by different developers, all editing the same infra:

Claude Code Codex Cursor
The task today

Production is complete. Staging has drifted - it's missing its DNS and SSO layer (4 components). The job: bring staging to parity with production, using all three tools.

Why each agent fails on its own

Duplication. Can't see a component already exists → builds a second one.
Broken conventions. Doesn't know the rules → writes a raw aws.s3.Bucket instead of the library wrapper.
Invisible blast radius. Can't see how things connect → changes a shared library, breaks prod two hops away.
Cold starts. The next tool/session re-derives everything and re-makes the same mistakes.
The fix: a shared, queryable memory in TiDB Cloud that every agent reads before it builds and writes back when it's done. No agent starts cold; none repeats another's work.

Three real coding tools, each loading the same two MCP servers, all reading and writing one TiDB Cloud database over the MySQL protocol. The dashboard is just a live window onto that same database.

Architecture
MCP = the standard plug. Each tool loads two servers: the official tidb MCP (raw SQL, vector, recursive CTE) and tidb-infra-kb (convention-checked reads/writes). No custom glue per tool.
One database, not four. Relational state, the dependency graph, vector embeddings, and full-text - all in the same TiDB tables, with ACID across concurrent writes from all three agents.
The dashboard reads the same DB. It's an observability window, not the system. Everything you see is a live query against TiDB.

This is what makes it automatic. Each tool loads a rules file (CLAUDE.md / AGENTS.md / .cursorrules) containing a standing instruction - so on every session, before any task, the agent already knows to read and write the shared memory. Nothing is hard-coded; this is configuration a team owns.

Standing instruction (loaded into every agent, every session)
Before writing any infrastructure code, query the tidb-infra-kb MCP first:
  - what components already exist (don't duplicate)
  - how they connect (dependency edges)
  - what previous sessions did (session_log)

Never use raw aws.* / cloudflare.* / okta.* resources - always compose the
reusable library components in libs/. Follow the acme-<env>-<name> naming
convention and apply the required tags (Environment, ManagedBy, Component, Team).

After you create or change anything, record it with write_component so the next
session - and the next tool - starts warm.
The MCP servers each tool connects to
{
  "mcpServers": {
    "tidb":          { "command": "uvx", "args": ["--from","pytidb[mcp]","tidb-mcp-server"] },
    "tidb-infra-kb": { "command": "python", "args": ["-m","src.mcp_server"] }
  }
}

tidb           -> official PingCAP MCP: db_query, db_execute (raw SQL, vector, CTE)
tidb-infra-kb  -> convention layer: query_knowledge_base, write_component (atomic)
Because it lives in the rules file, the "read first, write back" behavior happens on every run - across all three tools - with no per-task reminder.
