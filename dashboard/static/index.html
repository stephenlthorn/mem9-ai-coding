TiDB - Shared Memory Infrastructure
  • "Acme" platform team runs a Pulumi GitHub repo for IaC across AWS, Cloudflare, and Okta.
  • Code is written by AI coding agents.
  • Challenge: coding agents have no shared context.

The scenario

  • Pulumi monorepo
  • Reusable component libraries: S3Bucket, PostgresDatabase, DnsRecord, SsoApplication
  • PROD and staging environments

The agents

  • Three different AI coding tools, different developers, same infra:
Claude Code Codex Cursor

The task

  • Production is complete.
  • Staging has drifted - missing its DNS + SSO layer (4 components).
  • Bring staging to parity with production, using all three tools.

Why each agent fails on its own

  • Duplication - can't see a component exists → builds a second one.
  • Broken conventions - writes a raw aws.s3.Bucket instead of the library wrapper.
  • Invisible blast radius - changes a shared library, breaks prod two hops away.
  • Cold starts - the next session re-derives everything and re-makes mistakes.

The fix

  • A shared, queryable memory in TiDB Cloud that every agent reads before it builds and writes back when it's done. No agent starts cold; none repeats another's work.

Architecture - talking points

  • 3 real CLIs → MCP → one TiDB Cloud database (MySQL protocol).
  • MCP is the standard plug - no custom glue per tool.
  • Two servers: tidb (raw SQL, vector, CTE) + tidb-infra-kb (convention-checked writes).
  • One DB, not four: relational + graph + vector + full-text, ACID across concurrent writes.
  • The dashboard is a live window on the same DB - not the system.
Architecture
MCP = the standard plug. Each tool loads two servers: the official tidb MCP (raw SQL, vector, recursive CTE) and tidb-infra-kb (convention-checked reads/writes). No custom glue per tool.
One database, not four. Relational state, the dependency graph, vector embeddings, and full-text - all in the same TiDB tables, with ACID across concurrent writes from all three agents.
The dashboard reads the same DB. It's an observability window, not the system. Everything you see is a live query against TiDB.

System prompt - talking points

  • The behavior is configuration, not code.
  • Each tool loads a rules file: CLAUDE.md / AGENTS.md / .cursorrules.
  • Standing instruction, every session: query first → compose libraries → write back.
  • Happens automatically across all three tools - no per-task reminder.
Standing instruction (loaded into every agent, every session)
Before writing any infrastructure code, query the tidb-infra-kb MCP first:
  - what components already exist (don't duplicate)
  - how they connect (dependency edges)
  - what previous sessions did (session_log)

Never use raw aws.* / cloudflare.* / okta.* resources - always compose the
reusable library components in libs/. Follow the acme-<env>-<name> naming
convention and apply the required tags (Environment, ManagedBy, Component, Team).

After you create or change anything, record it with write_component so the next
session - and the next tool - starts warm.
The MCP servers each tool connects to
{
  "mcpServers": {
    "tidb":          { "command": "uvx", "args": ["--from","pytidb[mcp]","tidb-mcp-server"] },
    "tidb-infra-kb": { "command": "python", "args": ["-m","src.mcp_server"] }
  }
}

tidb           -> official PingCAP MCP: db_query, db_execute (raw SQL, vector, CTE)
tidb-infra-kb  -> convention layer: query_knowledge_base, write_component (atomic)
Because it lives in the rules file, the "read first, write back" behavior happens on every run - across all three tools - with no per-task reminder.

Dependency CTE - talking points

  • The question a vector DB can't answer: what transitively depends on this?
  • Pick a component → Blast radius (what breaks) or Dependencies (what it needs).
  • S3Bucket blast radius reaches the RDS databases two hops away (via backup buckets).
  • Plain recursive SQL on TiDB - graph reachability, not similarity.

Why TiDB - talking points

          
    
            
  • One engine, every access pattern: SQL + graph (CTE) + vector + full-text, no ETL.
    • 
            
  • ACID for agent state: component + edge + log in one transaction.
    • 
            
  • vs S3 / filesystem: no queries, no recursion, no transactions for concurrent writes.
    • 
            
  • vs multiple DBs: 4 systems to sync, no cross-system atomicity.
    • 
            
  • S3 is the filing cabinet for artifacts; TiDB is the brain.
